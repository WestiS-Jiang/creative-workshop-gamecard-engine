## 1. 核心产品定义与业务流 (Product & Business Logic)

- **项目一句话定位**：
  - 面向互动叙事创作者的 AI 原生内容生产工作台，将长篇小说自动解析为可推演的世界状态机、游戏设定文档与多阶段试玩体验。

- **目标用户与痛点**：
  - **目标用户**：互动叙事创作者、轻量游戏策划、网文/IP 改编团队、AI 内容创业者。
  - **核心痛点**：
    - 长篇小说改编为可玩内容时，人工拆世界观、角色关系、时间线和规则成本极高。
    - 传统 AI 写作工具只能生成一次性文本，不能沉淀为可迭代、可调试、可回放的结构化资产。
    - 长文档解析与多轮生成过程黑盒感强，创作者难以判断模型到底错在“哪一章、哪条设定、哪次冲突”。
    - 互动内容制作往往割裂在多个工具间，缺少“上传-解析-调试-生成-试玩-导出”的闭环工作流。

- **核心业务价值**：
  - 将非结构化小说资产转换为结构化内容底座，降低 AI 原生互动内容从 0 到 1 的制作门槛。
  - 通过“解析 + 仲裁 + 调试 + 推演”一体化能力，提升创作者验证设定与分支逻辑的效率。
  - 把原本依赖高经验策划的世界观整合、角色建模与叙事编排流程，产品化为可复用的标准链路。

- **MVP 核心链路**：
  - 上传 TXT/EPUB -> 前端切片与基线上下文准备 -> 发起后端全局解析 Job -> Map 阶段提取实体/事件/法则 -> Reduce 阶段冲突仲裁 -> 自动生成 RPG 属性与角色摘要 -> 创作者定制风格/角色/声音 -> 生成 Markdown 游戏卡 -> 从开头或锚点进入回合推演 -> 在双屏工作台中试玩与调试 -> 导出/发布内容资产。

- **核心业务闭环**：
  - **内容输入**：支持上传小说文本，前端做解析与切片。
  - **内容结构化**：后端对每个切片执行结构化抽取，并滚动注入 baseline context。
  - **世界观治理**：对章节间冲突设定执行多级仲裁，得到全局状态树。
  - **创作者定制**：支持时间步长、视觉风格、角色立绘、声音画像、游戏卡内容的人工干预。
  - **试玩验证**：通过回合引擎与 JSON Debugger 进行 What-if 测试。
  - **资产输出**：生成可下载的 `.md` 游戏卡，并可继续进入推演。

- **从代码可确认的产品边界**：
  - 已落地：
    - 长文本切片解析
    - 异步全局解析 Job
    - 暂停/恢复/轮询长任务
    - Map/Reduce 冲突仲裁
    - RPG 属性与角色摘要生成
    - 游戏卡 Markdown 生成
    - 受限问答助手
    - 回合推进与状态校验
    - Play-and-Debug 双屏
    - 多阶段 phase 渲染
    - 视觉风格推荐与角色重绘接口
    - 语音克隆入口占位
  - 暂未完全闭环或仍偏占位：
    - 真实语音克隆/远程 TTS
    - 更深的内容发布与分享后链路

## 2. AI 核心能力拆解 (AI Core & Agentic Workflow)

- **整体 AI 工作流总览**：
  - 输入小说切片后，系统并非只做一次大模型总结，而是拆成多个专用模型职责：
    - 结构化 Map 抽取
    - 事件流抽取
    - 隐性规则探测
    - 冲突补丁叙事生成
    - RPG 数值体系设计
    - 核心角色摘要
    - 视觉风格推荐
    - 游戏卡/GDD 生成
    - 文档协作问答
    - 实时回合叙事推进

- **模型职责分配**：
  - **Map 结构化抽取 Agent**：
    - 从章节文本提取实体、关系、属性、隐性规则候选。
    - 输出目标是 `EcsLocalGraph`，不是自然语言摘要。
    - 通过低置信度过滤控制脏数据进入全局状态树。
  - **Rule Probing Agent**：
    - 专门抽“社会阶级结构、能力消耗、因果铁律”，帮助系统建出世界法则层，而不仅是事件层。
  - **Event Extraction Agent**：
    - 抽章节事件、参与者、世界影响，用于事件图谱流。
  - **CRA Conflict Resolution Agent**：
    - 当冲突到达核心实体或硬冲突场景时，生成“补丁叙事”来平衡世界观一致性与可玩性。
  - **RPG Stat Design Agent**：
    - 基于隐性规则和角色画像自动定义适合该 IP 的核心属性模板，并为核心角色打初始值。
  - **Character Summary Agent**：
    - 将零散角色信息压缩为 biography/appearance，方便后续做角色选择、立绘、游戏卡排布。
  - **Visual Style Recommendation Agent**：
    - 基于题材、文件名和剧情摘要给出 4 套差异化风格，不是固定模板皮肤。
  - **Game Card Generation Agent**：
    - 把全局状态树、规则、角色池、时间线转译为策划级 Markdown 白皮书。
  - **Scoped Assistant Agent**：
    - 仅围绕当前 Markdown 游戏卡做问答与建议，不回答越界问题。
  - **Turn Narrative Agent**：
    - 在 `FOLLOW_CANON` / `SANDBOX` 双模式下负责每回合剧情推进、状态变化与可选动作生成。

- **Prompt 工程亮点**：
  - **严格的角色设定**：
    - 使用“世界观逆向解析引擎”“深层法则分析师”“RPG 数值策划”“Canon Director”“冷酷 TRPG DM”等角色化 system prompt，强化任务边界。
  - **结构化输出优先**：
    - 多数核心任务强制 JSON 输出，避免自然语言结果难以进入后续流水线。
  - **证据优先与反幻觉约束**：
    - Map 结构化抽取明确要求“必须以证据为唯一依据，严格避免幻觉和套路推演”。
  - **探针式 Prompt 设计**：
    - Rule Probing Prompt 不是泛泛总结，而是固定检查“权力与阶级投射、超凡能力资源依赖、因果铁律抽象”。
  - **模式化叙事 Prompt**：
    - `SANDBOX` 模式强调“原著已死，玩家至上，不允许强行贴回主线”。
    - `FOLLOW_CANON` 模式强调“软纠偏”而非简单拒绝偏航行为。
  - **场景型越界防护**：
    - 游戏卡助手限制只回答文档范围内容，越界时直接拒答。
  - **长上下文压缩策略**：
    - 游戏卡生成时对规则、时间线、角色候选和附加指令做截断、裁剪、去重，降低上下文爆炸风险。

- **多阶段 Agent 流拆解**：
  - **阶段 1：文本解析与切片**
    - 前端解析 TXT/EPUB，并按 chunk 切片。
  - **阶段 2：Map 提取**
    - 每片章节进入结构化抽取。
    - 成功则生成标准 local graph。
    - 失败则退到 legacy dual-stream。
    - 再失败则退到最小 fallback graph。
  - **阶段 3：Rolling Baseline**
    - 每个已解析切片的摘要会滚动注入下一轮 Map，减少长文本分块带来的上下文断裂。
  - **阶段 4：Reduce 冲突仲裁**
    - 对各切片 assertion 分组，按实体/属性键聚合冲突。
    - 使用多级规则选择保留值，必要时触发补丁叙事或 bifurcation。
  - **阶段 5：世界状态增强**
    - 基于 reduce 结果补 RPG 属性与核心角色摘要，提升后续可玩性和展示性。
  - **阶段 6：内容包装**
    - 自动生成游戏卡、视觉风格方案、角色立绘与声音配置草案。
  - **阶段 7：实时推演**
    - 将用户动作与当前状态送入 turn generator，生成新剧情和后续动作，再规范化并校验后写回存储。

- **工程级兜底策略 (Fallback)**：
  - **Map 三层兜底**：
    - Strict structured extract -> legacy dual-stream -> minimal fallback graph。
  - **低置信度过滤**：
    - 低于阈值的 entity update / relation edge 会被主动丢弃，避免污染全局图谱。
  - **切片失败隔离**：
    - Pipeline 统计 `failed_chunks`，并将失败信息写进 fallback metadata，方便复盘 bad case。
  - **CRA 补丁叙事兜底**：
    - 当硬冲突无法靠时序与密度裁决时，用单独的冲突解决代理生成补丁叙事。
  - **世界分叉标记**：
    - severe macro collapse 不强行统一，而是标记为 bifurcation，保留分叉可能性。
  - **Markdown 自修复**：
    - 游戏卡结构不合格会触发 repair 逻辑，最多多轮修复后再返回。
  - **回合输出规范化**：
    - 若 LLM 未完全按协议返回，会从 `plot_text / next_options / state_changes` 映射回标准 `game_state` 字段。
  - **默认选项兜底**：
    - 若模型未返回 `available_actions`，自动注入 `fallback_wait`。
  - **最终 Schema 校验**：
    - 回合结果走 AJV 校验，不合法直接阻断写库。
  - **网络重试与超时**：
    - 前端 API 层对 transient fetch error 重试。
    - 后端 provider adapter 对模型调用设置超时与 abort controller。
  - **大请求保护**：
    - 前端在发起全局解析前先估算 payload 大小，避免超出后端 body 限制。

- **可讲成“基础设施产品能力”的点**：
  - 模型调用统一收敛于 `llmService.ts`，业务模块不直连 API。
  - Provider Adapter 支持 OpenAI Compatible 与 Gemini 切换。
  - 任务级模型覆写由配置控制，而不是散落在业务代码里。

## 3. 人机交互与体验设计 (AI-Native UI/UX)

- **前端极速渲染策略**：
  - **四步门控工作流**：
    - 将创作流程设计为“导入 / 解析 / 定制 / 游戏卡”四步，防止用户在前置资产未完成时提前进入后续环节。
    - 这是典型的 AI 原生工作流设计，不是普通多 Tab UI。
  - **长任务 Job 化与轮询反馈**：
    - 全局解析不是单请求等待，而是 `create job -> poll -> pause/resume -> result apply`。
    - 通过阶段、进度、当前切片、提示文案减轻用户对“卡死/超时”的焦虑。
  - **暂停与续跑体验**：
    - 对 3~10 万字级解析任务引入暂停/恢复，适合在面试中讲成“把模型重活产品化”。
  - **动态等待文案**：
    - 游戏卡生成时循环显示不同 loading tips，把黑盒等待翻译成“剧情编织、关系校准、关键场景收束”等可感知过程。
  - **Phase Strategy 渲染架构**：
    - 不是用一堆 if/else 写死 UI，而是按 `current_phase` 映射不同 view，方便扩到开场/结尾视频、剧情动画等内容。

- **AI-Native 交互亮点**：
  - **Play-and-Debug 双屏工作台**：
    - 左屏给玩家视角叙事与动作，右屏给创作者视角 JSON 调试器。
    - 把“试玩体验”和“策划验证”合并为一个连续动作，而非两个工具切换。
  - **JSON Debugger（God Mode）**：
    - 用户可直接编辑完整状态树，强插人工判断修正模型误差。
    - 这是明显的人机协同节点，不让 AI 结果不可逆。
  - **从开头/锚点切入推演**：
    - 游戏卡支持从故事开头或锚点场景进入推演，有利于创作者快速验证关键桥段和高价值剧情节点。
  - **受限问答协作**：
    - 游戏卡生成后可进入“秘塔AI”问答模式，围绕当前文档做结构/文案/剧情编排优化。
  - **素材挂载与多模态预留**：
    - UI 已支持音频、视频、图片上传入口，以及角色声线与立绘相关操作，为多模态叙事演进预留交互骨架。

- **处理 AI 延迟与不确定性的产品设计**：
  - 不让用户面对单一的 loading spinner，而是拆成可观察任务状态。
  - 对解析失败、暂停状态、超时、请求体过大等问题提供可理解提示。
  - 将游戏卡生成与全局解析分别可视化，避免“一处生成卡住，全局都像坏了”。
  - [需补充：是否已有 skeleton screen、局部流式渲染或 chunk-by-chunk 预览]

- **人机协同与反馈 (HITL)**：
  - **人工状态修补入口**：
    - 通过 JSON Debugger 直接修改属性、关系、库存、状态字段。
  - **完整性报告**：
    - 回合推进会输出 `integrity_report`，帮助识别前端快照与持久态不一致问题。
  - **人工风格覆盖**：
    - 时间步长可手动覆盖，视觉风格可在推荐基础上二次编辑，声音画像可切换上传素材或 AI 随机。
  - **历史记录保留**：
    - 本地保存已处理小说历史，降低重复导入与反复试验成本。
  - **受限协作问答**：
    - 文档助手既能提供修改建议，又通过范围限制避免“对不该回答的问题乱答”。

- **可对外表达的 UX 价值**：
  - 解决了“AI 长任务白屏焦虑”
  - 解决了“创作者无法定位模型错误来源”
  - 解决了“AI 结果不可控、不可修、不可继续利用”
  - 解决了“内容生产工具之间割裂”

## 4. 容错、评估与治理机制 (Reliability, Evaluation & Guardrails)

- **反幻觉与一致性机制**：
  - 证据优先的 Map Prompt，尽可能将模型约束在可追溯文本片段上。
  - 低置信度过滤，不追求高召回而牺牲状态稳定性。
  - Reduce 阶段通过时序、证据密度与补丁叙事处理“吃书”和章节冲突。
  - 回合结果最终必须通过 schema 校验才写回状态库。

- **长尾 Case 兜底**：
  - 任一章节无法稳定抽取时，仍保留摘要型 fallback graph，确保全局任务尽量继续推进。
  - 模型未按格式返回时，可从兼容字段重组 game state。
  - 游戏卡结构异常时执行 repair，而不是直接把坏文档交给用户。

- **任务韧性设计**：
  - 全局解析支持 checkpoint 恢复。
  - Job 有 TTL 和最大缓存限制，避免服务端内存被长期任务拖垮。
  - 前后端都对网络/服务端瞬时错误做重试或提示。

- **可沉淀为数据飞轮的信号**：
  - 失败切片与错误信息
  - 冲突分组与 resolution logs
  - 被丢弃的低置信度字段
  - 玩家/创作者对状态树的人工 patch

- 推动统一 LLM Gateway 与 Provider Adapter 落地，实现业务层与模型供应商解耦，支持按任务切换模型、统一超时控制、统一结构化输出协议。
- 建立回合结果规范化与 AJV 校验机制，对不稳定的模型输出做结构映射、默认动作补齐和 schema 校验，降低非法状态写回风险。[需补充：异常拦截率]
- 为后续 Prompt 迭代与评测建设预留了失败切片、冲突日志、人工 patch 等关键反馈信号，具备形成 bad case 数据飞轮的基础。

### 选项 C：针对“AI 泛娱乐 / 前端交互 PM”

- 设计了适配 AI 长任务的四段式创作工作流，通过步骤门控、任务状态可视化与暂停恢复机制，显著降低复杂创作工具的学习与等待成本。
- 重构了互动叙事产品的前端架构，采用 phase-based rendering 支持 `INIT / INTRO / MAIN_LOOP / ENDING` 多阶段体验，为视频、BGM、立绘等多模态叙事扩展预留产品骨架。
- 打造了 Play-and-Debug 双屏工作台，把“玩家视角内容消费”与“创作者视角状态调试”合并在一个界面中，强化 AI 共创过程中的即时反馈与可控性。
- 为游戏卡生成、长文本解析等高延迟场景设计动态等待反馈与状态可视化，缓解用户对白屏、卡死和结果不确定的焦虑。
- 基于题材与文本信号自动推荐视觉风格，并串联立绘重绘、声音画像与素材挂载能力，把 AI 结果从单纯文本提升为具备感官包装力的内容资产。
- 设计并落地受限范围的文档协作问答助手，支持创作者围绕当前游戏卡进行结构与文案优化，同时通过越界拒答降低模型失控风险。

## 7. 面试追问准备 (Follow-up Questions You Should Expect)

- 为什么没有直接用一个大 Prompt 端到端生成游戏？
  - 因为长文本理解、冲突合并、数值设计、文档生成、回合叙事的目标函数不同，拆成多 Agent 才能兼顾稳定性、可解释性与后续评测。

- 为什么要做 Reduce 冲突矩阵？
  - 长文档不是单轮问答，章节间冲突是高频问题；如果没有规则化仲裁，状态树会被后续章节或模型幻觉轻易污染。

- 为什么要保留 JSON Debugger 这种“非傻瓜式”能力？
  - 目标用户是创作者和策划，他们需要对 AI 有最终控制权；越复杂的内容系统越不能只给“重新生成”按钮。

- 为什么要把游戏卡输出成 Markdown？
  - Markdown 兼顾可读、可编辑、可下载、可做问答上下文，也适合作为中间资产连接策划、生成与发布环节。

- 为什么要做 Phase 渲染，而不是一直停留在文本主循环？
  - 产品并不只想做文字选择器，而是为未来多模态叙事和可视化演出预留生命周期框架。
